# Contributing to Docentric Copilot

Thank you for considering a contribution. This project values correctness, reproducibility and
honesty over speed of delivery. Please read this document before opening a pull request.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). Security issues must be
reported privately as described in [SECURITY.md](SECURITY.md), not in a public issue.

## 1. Before you start

- **Open an issue first** for anything beyond a small fix: a new IR block, a new API endpoint, a new
  provider, a change to the compatibility gate, or a storage-format change. Design discussion is
  cheaper than a rejected PR.
- **Do not claim Docentric AX compatibility.** The gate is deliberate; see
  [docs/DOCENTRIC_AX_COMPATIBILITY.md](docs/DOCENTRIC_AX_COMPATIBILITY.md). A PR that weakens the gate
  or introduces compatibility language will be rejected.
- **Do not add third-party or customer data.** Fixtures must be synthetic and generated by
  `scripts/build_examples.py` or authored in `tests/golden_files/fixtures.py`.
- **All documentation, code comments, commit messages and examples must be in English.** No translated
  copies of documents are accepted.

## 2. Development setup

Requires Python 3.12+ (and Node 22+ only if you work on `apps/web`).

```bash
git clone https://github.com/SergeyGer/Docentric-Copilot
cd Docentric-Copilot

make install-dev          # or: python3.12 -m venv .venv && .venv/bin/pip install -e ".[dev]"
make test
make lint
make typecheck
```

Useful commands:

| Command | Purpose |
| --- | --- |
| `make test` | Run pytest |
| `make test-cov` | Branch coverage with the 85% gate |
| `make lint` | `ruff check` and `ruff format --check` |
| `make typecheck` | `mypy packages services` |
| `make format` | Auto-fix lint/format |
| `make bench` | Latency benchmark (writes `benchmarks/results.json`) |
| `make eval` | Planner evaluation with the mock baseline |
| `make openapi` | Regenerate `docs/openapi.json` |
| `make dev-api` | Run the API with autoreload on port 8000 |
| `make dev-web` | Run the web app on port 3000 |
| `make docker-up` / `make docker-down` | Local compose stack |
| `make ci` | lint + typecheck + coverage-gated tests |

## 3. Repository layout

One distribution, several source roots. Each directory maps to one subpackage of
`docentric_copilot` (declared in `pyproject.toml`).

| Directory | Import path | Area |
| --- | --- | --- |
| `packages/core` | `docentric_copilot` | Config, errors, ids, logging, serialization |
| `packages/ddsp-parser` | `.ddsp_parser` | Untrusted DDSP ingestion, XSD mapping, schema inference |
| `packages/schema-resolver` | `.schema_resolver` | Path/alias resolution, candidate search, mapping |
| `packages/template-ir` | `.template_ir` | IR models, canonical JSON, digest, migrations |
| `packages/template-validator` | `.template_validator` | V1–V5 engine and reports |
| `packages/docx-compiler` | `.docx_compiler` | DOCX compilation, package inspection, formatting |
| `packages/llm-gateway` | `.llm` | Provider adapters, gateway, pricing |
| `packages/planner` | `.planner` | Prompts, planning, sanitisation, revisions, baseline |
| `packages/renderer` | `.preview` | Independent HTML preview |
| `packages/evaluation` | `.evaluation` | Metrics for planner quality |
| `services/api` | `.app`, `.api`, `.cli`, `.storage` | Service, HTTP, CLI, persistence |
| `apps/web` | — | Next.js 15 frontend workspace (npm; port 3000) |
| `examples/` | — | Synthetic DDSP packages |
| `tests/` | — | Unit, integration, golden tests |

Dependency direction matters: foundation (`core`) must not import domain packages, `template_ir` must
not import the compiler, and only `planner`/`llm` may talk to a model. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## 4. Workflow

1. Create a branch from `main`: `feat/...`, `fix/...`, `docs/...`, `test/...`.
2. Add a failing test where possible, then implement.
3. Update the documentation that the change invalidates.
4. Run `make ci` (and `npm run lint && npm run typecheck && npm run build` in `apps/web` if you touched
   the frontend). There is no `npm test` script or committed browser E2E suite; a manual smoke run is
   not a substitute for tests. If you change UI behaviour that can be asserted headlessly, add a unit
   test or propose a committed Playwright suite in the PR.
5. Open a pull request using the template. Keep it focused; unrelated refactors make review harder.
6. Address review comments; do not force-push over a review unless asked.

Commit messages follow the existing style: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`,
with an imperative summary. Reference the requirement (for example `FR-05`) when applicable.

## 5. Definition of Done

A change is complete only when all of the following are true. This is the same Definition of Done as
[docs/SRS.md §5](docs/SRS.md#5-definition-of-done).

- [ ] **Behaviour tested.** At least one automated test fails without the change, or the PR explains
      why a test is impossible. Prefer unit tests for logic and integration tests for the API.
- [ ] **Lint and types pass.** `ruff check .`, `ruff format --check .`, `mypy packages services`.
- [ ] **Coverage gate passes.** `make test-cov` (85% branch coverage on the counted modules). Do not
      lower the gate without an ADR.
- [ ] **Documentation updated.**
      - IR model/field changes → `docs/TEMPLATE_IR.md` and `docs/SRS.md`.
      - Endpoint, status code or schema changes → `docs/API_SPEC.md` and regenerate
        `docs/openapi.json`.
      - Parser, diagnostic or limit changes → `docs/DDSP_COMPATIBILITY.md`.
      - Behaviour or feature-state changes → README feature matrix and `docs/ROADMAP.md`.
      - New decision → an ADR under `docs/adr/`.
- [ ] **No unverified compatibility claim.** Any mention of Docentric AX says "unverified", "not
      tested" or "blocked". The gate still returns HTTP 409 / exit code 4 and V5 is still `not_tested`.
- [ ] **No secrets or real data.** No API keys, customer data, third-party templates or proprietary
      DDSP packages in code, tests, fixtures, logs or screenshots.
- [ ] **Determinism preserved.** No clock, randomness, network access or unordered iteration in parse,
      validate, serialize or compile paths. Golden files updated only when the change is intentional.
- [ ] **Error contract coherent.** New failure modes have a `CopilotError` subclass, a stable code, an
      HTTP status, a CLI exit code (if reachable from the CLI) and an API_SPEC entry.
- [ ] **CHANGELOG.md** has an entry under `[Unreleased]` or the release version (user-visible changes
      only).
- [ ] **CI green** (`.github/workflows/ci.yml`) or `make ci` green locally with the output noted in the
      PR.

## 6. Code style

- Python 3.12, type hints on public functions, `from __future__ import annotations` is not required
  but common in the codebase.
- Line length 100; ruff rule set in `pyproject.toml` is authoritative.
- Pydantic models: `extra="forbid"` for contracts; explicit bounds on any string, list or nesting
  depth that accepts untrusted input.
- Errors: raise a typed `CopilotError` subclass with a stable code and structured details; never leak
  a raw provider response or secret in a message.
- Logging: use `get_logger(__name__)`; log identifiers and counts, never message content. Extra
  structured fields go under `extra={"context": {...}}` and are redacted automatically.
- Tests: no network, no sleeps unless unavoidable, no shared mutable state. Use
  `tests/conftest.py` fixtures; set `DC_DATA_DIR` for any storage access.
- Documentation: English only, specific, traceable to a file/symbol, no marketing language. If a
  number is unknown, write `TBD` and say how it will be measured.

## 7. Documentation rules

Documentation is part of the product contract:

1. **English only.** No Russian or other translated text, including examples and comments.
2. **Link evidence.** A behavioural claim should name a module/function or a test. Use relative links
   (for example `../packages/template-ir/...`).
3. **Do not invent features or metrics.** If something is not implemented, say so and point to the
   roadmap. If a metric is unmeasured, use `TBD` and define the measurement.
4. **Compatibility language.** Never write "verified", "certified", "works with" or "compatible" about
   Docentric AX. Use "unverified", "not tested", "blocked".
5. **JSON examples must be valid.** Keep them short and label abridged examples as abridged.
6. **Keep statuses in sync.** `docs/SRS.md`, README feature matrix, `docs/ROADMAP.md` and
   `docs/TEST_PLAN.md` must agree about what is implemented.

## 8. Tests and golden files

- Run the relevant subset first: `pytest tests/unit/test_ddsp_parser.py -q`.
- Golden fixtures live in `tests/golden_files/expected/`. Regenerate with:
  `python -m tests.golden_files.update_golden`, then **review every diff** before committing.
- Add a hostile-input test for every new parser construct (oversized, deeply nested, unsafe name,
  DTD/entity, nested archive).
- Compiler changes must keep byte-identical output for the same IR and sample data; assert it.
- Do not modify a test expectation to make a failing implementation pass unless the expectation itself
  was wrong; explain the change in the PR.

## 9. Security

- Report vulnerabilities privately per [SECURITY.md](SECURITY.md); do not open a public issue.
- Never commit `.env`, `.git-token`, provider keys or real customer data. `.gitignore` covers the
  common cases, but review your diff.
- New input surfaces must be bounded and must fail closed. Update
  [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) when you add a trust boundary.
- Logging changes must not log raw prompts, sample values or credentials.

## 10. Review and merge

- At least one maintainer review is required.
- Reviewers check the Definition of Done, not only the code.
- Squash or rebase to keep a clean history; the merge commit must not contain generated artifacts
  unless they are committed fixtures.
- A PR that changes the compatibility gate requires a new ADR and the evidence listed in
  `docs/DOCENTRIC_AX_COMPATIBILITY.md`. It will not be merged on code review alone.

## 11. Releases

Version numbers follow semantic versioning for the distribution; the IR has its own version. A release:

1. updates `CHANGELOG.md` (move `[Unreleased]` entries under the version, add the date);
2. bumps `version` in `pyproject.toml` and `__version__` in `packages/core`;
3. updates golden files only if the compiler version changed;
4. runs `make ci`, `make bench` and `make eval`;
5. tags the commit; `.github/workflows/release.yml` builds the wheel/sdist and both Docker images and
   attaches the distributions to the GitHub release (registry publishing is not configured).

No release may be published while the documentation claims an unverified compatibility.
