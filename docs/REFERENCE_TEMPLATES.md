# Reference Template Intelligence

> **Status: static inspection only.** The inspector reads reference templates, it does not run
> Docentric AX, compile native templates or prove runtime compatibility. Every report carries
> `runtime_compatibility: "not_tested"` and the AX gate stays fail-closed.

The reference inspector implements REF-00 (safe inventory and deduplication), REF-01 (real DDSP
schema evidence), REF-02 (Docentric metadata resolution), REF-03 (ReferenceGraph and a separate
read-only Reference IR), REF-04 (reference diff) and REF-05 (reference-based evaluation). The v0.10
P0 increment adds a D365 embedded-schema adapter and a canonical binding resolver that no longer
requires a standalone DDSP. The v0.11 P1 increment adds D365 evidence to the unified ReferenceGraph,
an opt-in safe Reference → Generic Template IR import, an independent visual diff, and report
persistence/reopen/export. It still exists so that real-world DOCX, DDSP, ZIP and AXPP packages can
be examined as evidence **before** any Docentric AX writer is attempted.

A report never enables `target=docentric-ax`: that request still returns HTTP `409`, and V5
compatibility is still `not_tested`. The v0.11 P1 import produces **generic DOCX IR** only; it is
not a native Docentric template and its visual diff is **LibreOffice rendering, not Word
fidelity**.

## REF-00 — safe inventory and deduplication

`inventory.py` accepts a `.docx`, `.zip`, `.axpp` or directory and returns a deterministic
manifest:

- source type and source SHA-256;
- one entry per artifact with virtual path, kind, size and SHA-256;
- exact duplicate groups (same SHA-256, multiple occurrences) without deleting provenance;
- nested archives, expanded only up to the requested depth;
- AXPP members normalized from backslash names (`Project\...`) to virtual `/` paths;
- platform hints (`ax2012`, `d365`, `mixed`, `unknown`) and ProductVersion strings when detectable;
- warnings for macros, ActiveX, embedded objects and external relationships. These are flagged,
  never opened or executed.

Security properties: archives are decompressed in memory under explicit size/entry/ratio limits;
encrypted entries, symlinks, absolute paths, drive paths, `..` traversal and oversized member names
are rejected; XML is parsed with DTDs, external entities and network access disabled; no expression
or XPath is evaluated; no macro, OLE object or external relationship is executed or fetched.

## REF-01 — real DDSP adapter

`ddsp_real.py` recognises a bare Docentric DDSP by its root element and namespace
(`dsp:dataSourcePackage` in `http://schemas.docentric.com/dynamics-ax/data-source-packages`), not
by the file extension. It maps the document onto the existing `NormalizedSchema` without changing
the synthetic parser API.

### What is extracted

| Evidence | Behaviour |
| --- | --- |
| Root and namespace | Recorded as `root_element` / `namespace`; any other root falls back to the v0.5 parser |
| Contract hints | `ProductVersion`, flavour/flavour label, language, template id, docu type id |
| Locales | Union of `dsp:design/dsp:languages` and label text languages; bounded, sorted |
| Labels | Label count and per-declaration `xse:label` text; a parent never inherits a child label |
| Data sections | `GeneralData`, `MainData` (and any other type) stay **separate sections**; two XSDs are never collapsed into one |
| Fields | XSD attributes become path-addressable `@Name` leaves, e.g. `MainData.Order.Lines.Line.@Sku` |
| Types | `xs:string`, `decimal`, `integer`, `long`, `boolean`, `date`, `dateTime`, `base64Binary`, `anyURI` and the other v0.5 mappings |
| Collections | Own `maxOccurs` **and** inherited `choice`/`sequence`/`all` cardinality, including nested repeating groups |
| Sample values | First occurrence from `dsp:data`, coerced by type; binary/image values are not copied |
| Unsupported constructs | Explicit list in `schema_evidence.unsupported_constructs`; never dropped silently |

Malformed XML fails with `reference_xml_invalid`; DOCTYPE/entity content is rejected before
parsing; file size, XML node count and depth are bounded by `reference/safety.py`. The parser
carries the raw XPath in each node's `source` for review and does not evaluate it.

The v0.5 synthetic parser remains the fallback for a bare XSD, sample-data inference and synthetic
ZIP packages. `parse_ddsp_schema()` is the dispatcher used by the inspector; `parse_real_ddsp()`
accepts only the real contract.

`reference inspect --schema-report` prints the evidence per document. The same evidence is stored
under `documents[*].schema_evidence` in the JSON report, so schema statistics are available without
embedding a multi-thousand-node schema in every report.

## REF-02 — content controls and metadata resolver

`docx_controls.py` scans `word/document.xml`, headers, footers, footnotes, endnotes, comments and
the glossary story part. Every `w:sdt` becomes one record with part/story, paragraph, ordinal,
depth, alias, tag, signed and unsigned ids, Word control type, placeholder, text preview,
`w:dataBinding` evidence and a classification of `recognized`, `ambiguous` or `unknown`.

`metadata.py` finds ProjectData by namespace in any `customXml/itemN.xml`, maps `storeItemID`
through `itemProps`, canonicalizes the signed SDT id to the unsigned `Element/@Id`, and resolves
typed `ValueBinding` paths against the optional DDSP schema. List-relative `Source="."` bindings are
resolved through enclosing elements and become explicit `relative_binding_ambiguous` /
`relative_binding_unresolved` diagnostics rather than guesses.

Unresolved controls are never discarded. Each control reports `resolved`, `missing_part`,
`unknown_path` or `ambiguous`, with link/path statuses and diagnostic codes kept separately from
the overall status.

## D365 embedded schema and binding resolution (v0.10 P0)

D365 examples do not ship one standalone DDSP per document. The schema is embedded in
`customXml/itemN.xml` as Docentric `ProjectData`:

```
ProjectData
  DataSources/DataSource[@Name, @dataSectionType]
    Schema/XsdList/MainXsd/xs:schema     # fields, types and cardinality
    Schema/XmlNamespaceMappings          # declared path prefixes
    PreviewData/SampleXml                # sample instance (corroboration only)
  Elements/Element[@Id, @Type]           # ValueBinding facts to resolve
```

`d365_schema.py` reads only what is present and attaches OOXML provenance to every fact: the part,
an XPath-like location and a stable source id. `binding_resolver.py` matches the typed facts against
the canonical schema. Neither module executes an expression, opens the network, or turns a missing
piece of evidence into a success.

### Schema classification

| `schema_source` | Condition |
| --- | --- |
| `projectdata` | At least one embedded DataSource yields a usable XSD schema |
| `ddsp` | No usable embedded schema, but a caller-supplied DDSP yields a usable section |
| `unavailable` | Neither source has enough evidence; the report says so explicitly |

Absence of a standalone DDSP is not by itself a failure. A document with a complete embedded schema
is checked without one. Embedded schema is primary; a supplied DDSP is a fallback and never silently
merged.

### Binding statuses

| Status | Meaning |
| --- | --- |
| `resolved` | Source, canonical path, collection scope and type were all verified against schema evidence |
| `ambiguous` | More than one admissible binding, duplicate source/path or unresolved relative context |
| `unknown_path` | Schema is available, but the path, source or scope is absent or invalid in this context |
| `type_mismatch` | The path was found, but the declared result type or element role conflicts with the schema type (for example a boolean conditional on a string field, or a scalar field on a collection) |
| `schema_unavailable` | Neither embedded ProjectData nor a supplied DDSP carries enough schema |
| `unsupported_expression` | The path uses semantics this resolver does not evaluate (functions, comparisons, predicates, aggregates, undeclared or non-data namespace prefixes) |

A `resolved` result stores `source_id` and an `evidence` string of the form
`customXml/item1.xml#/ProjectData/...`, so every success can be traced to a concrete schema node.
Duplicate sources and duplicate paths are diagnostics, never a success. Relative `Source="."`
bindings require an enclosing `List` with a resolvable collection binding; a missing or
non-collection context is `unknown_path`.

### Result contract

```json
{
  "template_id": "<sha256 of the DOCX>",
  "platform": "D365FO",
  "schema_source": "projectdata",
  "schema_evidence": ["customXml/item1.xml#/ProjectData/..."],
  "binding_results": [
    {
      "element_id": "...",
      "status": "resolved",
      "raw_path": "@Number",
      "canonical_path": "MainData/Root/@Number",
      "source_id": "customXml/item1.xml#dataSource[1]",
      "evidence": "customXml/item1.xml#/ProjectData/..."
    }
  ],
  "runtime_compatibility": "not_tested"
}
```

The report additionally carries deterministic counts, a schema summary and diagnostics. Schema
models expose fields, collections, scopes, XSD types, type families, namespaces, preview repetitions
and the raw/canonical path pair.

### Security boundary

The adapter reuses the REF-00 limits: ZIP entry count, uncompressed size, compression ratio,
encrypted entries, symlinks and traversal are rejected; XML is parsed with DTDs, external entities
and network access disabled; node count and depth are bounded. The adapter also bounds customXml
parts, DataSources, schema nodes, collections, preview nodes and diagnostics. Every truncation is
reported. Inputs are never executed, and malformed ProjectData becomes a diagnostic (or a clear
`reference_container_invalid` / `reference_xml_invalid` error for a malformed container).

## REF-03 — ReferenceGraph and read-only projection

### Graph contract

`graph.py` builds `ReferenceGraph` v1.0 from the inspector report plus the per-document schema
artifacts. Nodes are stable, sorted identifiers:

| Node kind | Meaning |
| --- | --- |
| `control` | One OOXML content-control instance with part, paragraph, ordinal and depth |
| `element` | One typed ProjectData element (`Field`, `List`, `If`, `Image`, `Label`, `Barcode`, `SummaryField`, `SubDocument`, `Group`) |
| `source` | One ProjectData part + data-source name (`GeneralData`, `MainData`, `Parameters`, …) |
| `schema_field` | One normalized DDSP path with data type and collection flag |

Edges are directed and typed:

| Edge | From → to | Meaning |
| --- | --- | --- |
| `bound_to` | control → element | Technical id join from REF-02 |
| `bound_to` | element → source | The ProjectData scope that supplies the element |
| `resolves_to` | element → schema_field | Binding path matched against the DDSP schema |
| `iterates` | List/Group → child element | Detected repeated-section structure |
| `condition` | If → child element | Detected conditional structure |

Every node and edge carries `resolved`, `ambiguous` or `unknown`. Unknown paths become explicit
schema-field placeholders; stale `ChildElements` references become explicit missing-element nodes.
`ChildElements` traversal is cycle-cut with a `graph_child_element_cycle` diagnostic, so
serialization is always acyclic and deterministic. `graph_digest` covers the normalized graph with
no timestamps, hostnames or absolute paths.

The summary reports node/edge counts by kind and status, control denominators
(`controls_total = resolved + ambiguous + unknown`), emitted-edge coverage, unresolved-node count,
list/condition counts and schema-field counts.

### Read-only Reference IR

`projection.py` projects the graph into `ReferenceDocument`, a **separate contract**:

```
ReferenceDocument
  ir_kind = "reference"
  compilable = false
  template_ir_compatible = false
  runtime_compatibility = "not_tested"
  sections[] -> elements[]
      display_label, kind, binding_path, status, capability
      source_location {part, ordinal, paragraph_index, depth}
      source_name, schema_path, data_type, collection
```

Capabilities follow the reference-only boundary: `reference_only` for recognized/resolved
elements, `recognized` for known-but-unresolved elements, `unsupported` for unknown controls.
`importable` exists in the vocabulary but is never emitted in v0.6 because no import mode exists.
The projection is not Template IR, is not compilable, and preserves ambiguous/unknown elements
with their reasons.

## REF-04 — reference diff

`diff.py` compares two read-only `ReferenceGraph`s. It also accepts two inspection bundles, two
reports or two reference paths; the path form builds the graphs with the same bounded inspector and
optional `--ddsp` schema. `ReferenceDiff` v1.0 is a comparison contract, not Template IR: it has
`compilable: false`, `runtime_compatibility: "not_tested"` and a deterministic `diff_digest`.

### Stable keys and items

Keys do not contain the document SHA-256 or absolute paths, so a renamed copy or a binding change
does not relocate the whole comparison:

| Item kind | Stable key basis |
| --- | --- |
| `control` | part + ProjectData/SDT id (or paragraph/ordinal for an unbound control) |
| `element` | ProjectData part + element id |
| `binding` | the owning element's stable key |
| `source` | part + data-source name |
| `schema_field` | normalized schema path |

A changed item carries `before` and `after` snapshots with kind, binding path, resolution status,
part, paragraph, source, data type and collection flag, plus the `fields` that actually changed.

### Structural versus semantic

- **Structural**: added/removed items, part changes and paragraph moves. Count and part deltas are
  reported separately in `counts`.
- **Semantic**: binding path, resolution status, element kind, source, data type and collection
  changes. A change with both aspects is classified semantic; its `fields` list still names the
  structural aspect.

The summary reports added/removed/changed/ambiguous totals, per-kind and per-dimension counts,
status transitions (for example `resolved->ambiguous`), edge/control coverage before and after,
the unresolved delta with the stable keys that appeared or disappeared, and a canonical digest.
Items are sorted by item kind, change type, stable key and dimension, so two runs over the same
inputs are byte-identical.

### CLI and HTTP

```bash
docentric-copilot reference diff left.docx right.docx --json .tools/diff.json
docentric-copilot reference diff older.docx newer.docx \
  --ddsp schema.ddsp --json .tools/diff.json
```

```text
POST /api/v1/reference/diff
```

Use two multipart fields `left` and `right`, optionally with a shared `ddsp` upload, or the query
parameters `left_path` and `right_path` inside a configured corpus root. Mixing uploads and paths
is rejected. The endpoint is read-only and never enables the AX target.

The public test fixture is a synthetic pair where one binding path changes (semantic), one control
is added (structural) and one control becomes ambiguous because its element id is duplicated
(semantic). The tests assert the classification, canonical ordering and digest stability; they do
not open the real corpus.

## REF-05 — reference-based evaluation

`benchmarks/reference_evaluation.py` scores a generated or supplied plan against reference
patterns. It maps inspected controls/elements as follows:

> REF-05 is **not** the v0.10 P0 gold benchmark from PR-04/PR-05. REF-05 compares a plan with the
> patterns observed in a reference template; the gold benchmark scores prompt-to-template business
> semantics against a versioned 32-case dataset. See [GOLD_LABELS](GOLD_LABELS.md) and
> [EVALUATION §2.7](EVALUATION.md#27-gold-semantic-benchmark-v010-pr-05).

| Reference pattern | Expected concept | Produced evidence |
| --- | --- | --- |
| Field | scalar | field binding |
| List | collection | repeat/table collection |
| If | condition | conditional expression |
| Image | image | image binding |
| Label | text | field binding (text role) |

### Gold set

`benchmarks/reference_cases.json` contains eight synthetic, hand-authored cases: Field scalar,
Field date, List collection, If condition, Image logo, Label text, header/body/footer context and a
mixed invoice. They contain 41 expected concepts across the five patterns. The DOCX and DDSP
fixtures live under `benchmarks/fixtures/reference/` and are generated deterministically by
`benchmarks/reference_fixtures.py`; they contain no Docentric archive content. The evaluator also
derives the concept inventory from each synthetic reference and reports any disagreement with the
gold set, so the mapping is checked rather than assumed.

### Metrics

| Metric | Meaning |
| --- | --- |
| `precision` | produced reference-relevant bindings that match an expected concept / all produced |
| `recall` | matched required concepts / required concepts |
| `coverage` | matched concepts / all expected concepts, including optional ones |
| `f1` | harmonic mean of precision and recall |
| `type_context_correctness` | type and placement checks passed / checks performed |
| `valid_template_rate` | plans that validate and compile / runs (reported separately, never folded in) |

Every run records an error taxonomy (`missing_field`, `wrong_binding`, `wrong_context`,
`unsupported_expression`, provider and harness codes), produced paths, expected/forbidden paths and
a per-concept outcome. Cost is three-valued: `verified`, `estimated` or `unavailable`; mock runs are
verified at zero and unknown is never displayed as `$0.00`.

### Modes

```bash
# Synthetic CI mode: deterministic mock, no paid calls.
.venv/bin/python benchmarks/reference_evaluation.py --provider mock

# Optional quick run or an existing plan.
.venv/bin/python benchmarks/reference_evaluation.py --limit 2 --provider mock
.venv/bin/python benchmarks/reference_evaluation.py \
  --reference .tools/reference-corpus/runtime/example/Template.docx \
  --ddsp .tools/reference-corpus/runtime/example/Template.ddsp \
  --plan .tools/plan.json --provider mock

# Runtime-only local-corpus mode, generating the plan with the mock baseline.
.venv/bin/python benchmarks/reference_evaluation.py \
  --reference .tools/reference-corpus/runtime/example/Template.docx \
  --ddsp .tools/reference-corpus/runtime/example/Template.ddsp \
  --prompt-file .tools/prompt.txt --provider mock \
  --output-json .tools/reference-corpus/reports/template.json
```

`--cases` and `--reference` are separate modes. `--reference` derives expectations from the
inspected reference at runtime; `--ddsp` supplies the schema. A non-mock provider requires
`--allow-paid` and reports the observed cost status from token usage. The evaluator writes JSON,
CSV and HTML with sample size, provenance (`synthetic` or `local-corpus`), pattern counts, error
taxonomy and cost status.

### #26 — D365 evidence in the unified ReferenceGraph

`build_reference_graph` accepts either explicit D365 binding reports or the original DOCX payloads:

```python
from docentric_copilot.reference import (
    analyze_d365_bytes,
    build_reference_graph,
    inspect_reference_bundle,
)

bundle = inspect_reference_bundle("reference.docx")
d365 = analyze_d365_bytes(open("reference.docx", "rb").read(), filename="reference.docx")
graph = build_reference_graph(bundle.report, bundle.schemas, d365={d365.template_id: d365})
# or let the graph extract the embedded schema read-only from the payloads:
graph = build_reference_graph(bundle.report, bundle.schemas, documents=bundle.payloads)
```

- `schema_field` nodes carry `schema_source` (`ddsp` or `d365_project_data`), `source_id`,
  `schema_path`, `data_type`, `collection` and `evidence_location` (`part#xpath`).
- `resolves_to` edges carry `resolution_status` = `resolved | ambiguous | unknown_path |
  type_mismatch | schema_unavailable | unsupported_expression`. Only `resolved` gets graph status
  `resolved`; `type_mismatch`, `schema_unavailable` and `unsupported_expression` stay unresolved
  diagnostics and are never reclassified as `unknown_path`.
- `GraphSummary` adds `resolves_to_edges`, `resolves_to_resolved`, `resolves_to_with_evidence`,
  `evidence_coverage_ratio` (resolved edges with evidence / all `resolves_to` edges),
  `unresolved_by_status` and `unresolved_reasons`.
- AX 2012 DDSP docs keep the existing DDSP schema paths. When both providers are used across a
  multi-document source, the graph reports `schema_source: mixed` and both provider types.
- Determinism: nodes and edges are sorted, evidence is bounded, and repeated builds produce the
  same `graph_digest`.
- Partial: the committed tests use synthetic D365-like ProjectData; the local 11-DOCX corpus was
  not re-run in this branch, so graph coverage of that corpus is not claimed as verified here.

### #27 — safe Reference → Generic Template IR import

`project_to_template_ir(reference_document_or_graph, *, allow_unsupported=False)` is opt-in and
produces a `ReferenceIRImport` envelope:

| Reference construct | Generic IR mapping | Conditions |
| --- | --- | --- |
| Field | `FieldBinding` | unambiguous `resolved` binding with schema path; format defaults follow the type (`number`, `date_short`, `boolean_yes_no`, `plain`) |
| Label | `TextRun` | resolved element with captured static label text; a raw data path without a label is skipped |
| List | `Repeat` | confirmed collection scope; children projected recursively |
| If | `Conditional` | evidence-backed boolean field; condition is `equals true` |
| Image | `ImageBinding` | confirmed binary/image schema type only |

Everything else (Barcode, Group, SubDocument, SummaryField, complex expressions, unknown kinds,
ambiguous/unknown/type-mismatch/schema-unavailable/unsupported bindings, empty collections) is
listed in `skipped[]` with a stable code, location and reason. Strict mode (default) raises
`reference_import_blocked` if anything was skipped; `allow_unsupported=True` keeps the supported
subset and returns every skip. It never converts an unsupported construct into a guess.

The produced `Document` is validated with the existing V1-V3 `ValidationEngine` against a synthetic
schema containing only the imported, evidence-backed paths. A validation failure raises
`reference_import_invalid` with statuses and findings. The IR target is `generic-docx`; the response
includes `runtime_compatibility: not_tested`.

`ReferenceIRImport` also returns `provenance[]` keyed by stable IR path
(`sections[0].body[2].blocks[0]...`) with source reference id, element id, part/ordinal, raw and
canonical path, schema source, source id and `part#xpath` evidence. Template IR v1.0 is frozen, so
this sidecar is used instead of adding fields that would change every existing IR digest.

CLI:

```bash
docentric-copilot reference import-ir template.docx --json .tools/import-ir.json
docentric-copilot reference import-ir template.docx --allow-unsupported \
  --json .tools/import-ir.json
docentric-copilot reference import-ir template.docx --ddsp fallback.ddsp \
  --json .tools/import-ir.json
```

HTTP: `POST /api/v1/reference/import-ir` accepts the same multipart `file`/`ddsp` (or corpus
`?path=`) plus `allow_unsupported=true|false`. The response contains `ir`, `skipped`,
`provenance`, `validation`, `summary` and `runtime_compatibility: not_tested`.

Partial: List is projected to `Repeat`, not `Table`; Group/SubDocument/Barcode/SummaryField and
complex expressions remain reference-only; labels are imported as static text rather than dynamic
Docentric labels.

### #28 — independent visual reference diff

The structural/semantic diff (`reference diff`) is unchanged. The visual dimension is a separate
report produced by `scripts/reference_visual_diff.py` and the reference package:

```bash
python scripts/reference_visual_diff.py before.docx after.docx --json out/report.json
docentric-copilot reference visual-diff before.docx after.docx --json out/report.json
```

It renders both references through the existing `scripts/docx_to_pdf.py` LibreOffice path
(`soffice --headless --convert-to pdf` + `pdftoppm`), then reports:

- page counts and page-size changes;
- blank pages and per-page ink/coverage deltas;
- a coarse changed-pixel fraction within a fixed tolerance;
- shifted regions from a bounded grid search (offset in pixels and improvement);
- `report.json` and `report.html` plus PDF/page-image artifact paths.

The report always states **LibreOffice rendering (not Word fidelity)** and keeps
`structural_status`/`semantic_status` at `not_compared`; run `reference diff` for those independent
dimensions. A visual difference is evidence, not a defect verdict.

When `soffice`/`poppler` is missing or rendering fails, `visual_status` is `renderer_unavailable`
with a reason. It is never `passed`/`failed`, and no baseline is fabricated. The committed test
suite exercises the deterministic PNG comparison and the unavailable path with a stub renderer; CI
has no LibreOffice, so real-renderer output is not a CI gate here.

Partial: this is not a Word-layout validator, does not compare text/geometry semantically page by
page, and has no pinned font set beyond the optional `api-pdf` image.

### #29 — persistence, reopen and export

A new SQLite table `reference_reports` stores the serialized report/graph/diff envelope with a TTL
(`DC_ARTIFACT_TTL_SECONDS`, default 3600 s). Only JSON evidence is stored; source template bytes are
never written to the database or artifact storage.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/reference/reports?kind=inspection\|graph\|diff` | Run server-side and persist with an id |
| `GET` | `/api/v1/reference/reports/{id}` | Reopen by id (404 when missing/expired) |
| `GET` | `/api/v1/reference/reports/{id}/export?format=json\|html` | Download the full JSON or safe HTML |

The HTML export is self-contained, has no external assets or source active content, and HTML-escapes
every value including source names and warnings. The envelope includes versions, hashes, platform,
statuses, metrics, warnings and `runtime_compatibility: not_tested`.

The `/reference` web page saves the last report id in `?id=`, reloads it through
`GET /reports/{id}`, handles absent/invalid ids without crashing, and offers an **Export report**
action (JSON or HTML). It does not perform a browser E2E smoke; that remains a follow-up.

Partial: local single-process SQLite with TTL; no retention/delete endpoint beyond expiry, no
multi-process store and no committed Playwright workflow.

## Report

`report.py` produces `ReferenceReport` (reference version `1.0`) with:

- artifact/document/control counts and counts per element kind, classification, resolution,
  link status, path status, part and story;
- `coverage_ratio` = fully resolved controls / all controls (0.0 when a document has no controls);
- `join_coverage_ratio` = controls joined by id / all controls;
- per-document bounded `metadata_elements` and `schema_evidence` for REF-03;
- exact duplicate groups and nested-archive inventory;
- a stable `report_digest` over canonical report content;
- a per-control diagnostics trail and `runtime_compatibility: "not_tested"`.

Lists are sorted and JSON output uses sorted keys. The denominator is always reported explicitly,
so coverage cannot be silently inflated by duplicate copies.

## CLI

```bash
# local DOCX
docentric-copilot reference inspect template.docx --json .tools/report.json

# a whole directory, expanding two nested archive levels
docentric-copilot reference inspect .tools/reference-corpus/examples/corpus \
  --max-depth 2 --json .tools/report.json

# provide a real DDSP schema and show REF-01 evidence
docentric-copilot reference inspect template.docx \
  --ddsp template.ddsp --schema-report --json report.json

# build the read-only ReferenceGraph and optional Reference IR projection
docentric-copilot reference graph template.docx \
  --ddsp template.ddsp --json .tools/graph.json \
  --projection .tools/reference.json

# graph JSON to stdout
docentric-copilot reference graph template.docx --json -

# compare two references (REF-04)
docentric-copilot reference diff left.docx right.docx --json .tools/diff.json

# D365 embedded schema + canonical binding resolution (v0.10 P0)
docentric-copilot reference d365 template.docx --json .tools/d365.json

# the DDSP is a fallback only when the document has no usable embedded schema
docentric-copilot reference d365 template.docx --ddsp fallback.ddsp --json .tools/d365.json

# safe Reference -> Generic Template IR (v0.11 P1)
docentric-copilot reference import-ir template.docx --json .tools/import-ir.json
docentric-copilot reference import-ir template.docx --allow-unsupported \
  --json .tools/import-ir.json

# independent visual diff through LibreOffice (not Word fidelity)
docentric-copilot reference visual-diff left.docx right.docx \
  --json .tools/visual-diff/report.json
# renderer_unavailable is exit 0 and never a pass/fail
```

`--max-depth` is offline-only and capped at 3. Exit codes follow the existing CLI contract:
`0` success, `3` invalid/unsupported input, `6` missing input.

## HTTP API

```
POST /api/v1/reference/inspect
POST /api/v1/reference/graph
POST /api/v1/reference/d365
POST /api/v1/reference/diff
```

`inspect`, `graph`, `d365` and `import-ir` accept either an uploaded multipart `file`
(`.docx`, `.zip`, `.axpp`) with an optional `ddsp` part, or `?path=` for a path confined to a
configured corpus root. `diff` uses the `left`/`right` uploads or the `left_path`/`right_path`
query pair. Query parameter `max_depth` defaults to `0` for the public endpoints: the root container
is enumerated, but nested archives are not expanded. The existing `max_ddsp_bytes` limit is enforced
for uploads and the uncompressed/entry limits are enforced while reading.

The v0.11 P1 persistence endpoints are separate: `POST /api/v1/reference/reports` runs the
inspection server-side and stores the envelope, `GET .../reports/{id}` reopens it and
`GET .../reports/{id}/export?format=json|html` downloads the safe export. They follow the same
TTL/retention rules as artifacts and never store source template bytes.

```bash
curl -s -F "file=@template.docx" \
  http://localhost:8000/api/v1/reference/inspect

curl -s -F "file=@template.docx" -F "ddsp=@template.ddsp" \
  http://localhost:8000/api/v1/reference/graph

curl -s -F "file=@template.docx" \
  http://localhost:8000/api/v1/reference/d365

curl -s -F "file=@template.docx" \
  "http://localhost:8000/api/v1/reference/import-ir?allow_unsupported=false"

curl -s -F "file=@template.docx" \
  -F "ddsp=@fallback.ddsp" "http://localhost:8000/api/v1/reference/import-ir"

curl -s -F "file=@template.docx" \
  "http://localhost:8000/api/v1/reference/reports?kind=inspection"

curl -s "http://localhost:8000/api/v1/reference/reports/ref_.../export?format=html" \
  -o reference-report.html

curl -s -X POST \
  "http://localhost:8000/api/v1/reference/graph?path=examples/corpus/template.docx&max_depth=0"
```

Corpus roots are configured with `DC_REFERENCE_CORPUS_ROOTS` (comma-separated) and default to the
git-ignored `.tools/reference-corpus`. Symlinks and `..` cannot escape a configured root.

The read-only projection is available through the Python API (`project_graph`, `projection_json`)
and the CLI `--projection` option. It is intentionally not a compiler endpoint.

The diff endpoint accepts two multipart fields `left` and `right` (with an optional shared `ddsp`)
or two corpus-confined query paths:

```bash
curl -s -F "left=@left.docx" -F "right=@right.docx" \
  -F "ddsp=@schema.ddsp" http://localhost:8000/api/v1/reference/diff

curl -s -X POST \
  "http://localhost:8000/api/v1/reference/diff?left_path=left.docx&right_path=right.docx"
```
