# Reference Template Intelligence

> **Status: static inspection only.** The inspector reads reference templates, it does not run
> Docentric AX, compile native templates or prove runtime compatibility. Every report carries
> `runtime_compatibility: "not_tested"`.

The reference inspector is the v0.6 milestone-A implementation of REF-00 (safe inventory and
deduplication) and REF-02 (Docentric metadata resolution). It exists so that real-world DOCX,
DDSP, ZIP and AXPP packages can be examined as evidence **before** any Docentric AX writer is
attempted.

## Licensing boundary

The Docentric example archive is vendor material and is **not part of this repository**.

- The official corpus is copied only to the git-ignored working directory `.tools/reference-corpus/`
  (also covered by `.tools/` in `.gitignore`).
- No file, fragment, schema, template text or screenshot from that archive is committed here or
  embedded in tests, documentation or fixtures.
- The public test suite uses synthetic DOCX, AXPP/ZIP and DDSP payloads generated by
  `tests/reference_fixtures.py`. The tests never open the real corpus.
- Reports produced from a real corpus may contain template text and business-shaped metadata.
  Keep them under `.tools/`/another private location and do not commit them.
- Redistribution of the official examples requires a licence review; static inspection does not
  grant that right.

## What the inspector does

### REF-00 — safe inventory and deduplication

`inventory.py` accepts a `.docx`, `.zip`, `.axpp` or directory and returns a deterministic
manifest:

- source type and source SHA-256;
- one entry per artifact with virtual path, kind, size and SHA-256;
- exact duplicate groups (same SHA-256, multiple occurrences) without deleting provenance;
- nested archives, expanded only up to the requested depth;
- AXPP members normalized from backslash names (`Project\...`) to virtual `/` paths;
- platform hints (`ax2012`, `d365`, `mixed`, `unknown`) and ProductVersion strings when they are
  detectable from paths or XML;
- warnings for macros, ActiveX, embedded objects and external relationships. These are flagged,
  never opened or executed.

Security properties:

- archives are decompressed in memory under `max_ddsp_bytes`, `max_uncompressed_bytes`,
  `max_zip_entries` and `max_compression_ratio` limits;
- encrypted entries, symbolic links, absolute paths, Windows drive paths, `..` traversal and
  oversized member names are rejected;
- XML is parsed with DTDs, external entities, network access and XInclude disabled, and with node
  and depth bounds;
- no expression or XPath from a template is evaluated; no macro, OLE object or external
  relationship is executed or fetched;
- source paths recorded inside ProjectData (for example `C:/...`) are metadata only and are never
  used for filesystem access.

### REF-02 — content controls and metadata resolver

`docx_controls.py` scans `word/document.xml`, headers, footers, footnotes, endnotes, comments and
the glossary story part. Every `w:sdt` becomes one record with:

- part, story kind, paragraph index, ordinal and nesting depth;
- alias, tag, signed `w:id` and unsigned 32-bit form;
- Word control type (`text`, `date`, `dropdown`, `picture`, and the other detected variants);
- placeholder, text preview, `w:dataBinding` XPath/storeItemID/prefix mappings;
- marker evidence and a classification of `recognized`, `ambiguous` or `unknown`.

Classification is heuristic and never silent. Known Docentric labels
(Field/List/If/Image/Label/Barcode/SummaryField/SubDocument/Group), `#` markers and used
`dc`/Docentric namespaces are recorded. Controls with conflicting evidence are `ambiguous`;
controls with no recognizable Docentric marker are still returned as `unknown`.

`metadata.py` then joins the control to Docentric `ProjectData`:

1. Find ProjectData by namespace/root in any `customXml/itemN.xml` part — item numbers are never
   hard-coded.
2. Map `w:dataBinding/@storeItemID` to the matching customXml part through `itemProps`.
3. Canonicalize the signed SDT id (`-1964797487` → `2330169809`) and join it to `Element/@Id`.
4. Keep duplicate or shared ids visible; only conflicting metadata for the same id is
   `ambiguous`.
5. Resolve `ValueBinding` paths against an optional bare DDSP XML schema, including root-relative
   paths, list-relative `Source="."` paths, namespace prefixes and expression heuristics.

Each control receives one of:

| Status | Meaning |
| --- | --- |
| `resolved` | Metadata joined and, when a schema was supplied, the path matched. |
| `missing_part` | ProjectData or the storeItemID-referenced customXml part is absent. |
| `unknown_path` | Metadata joined but the path/section is unknown, or no Element matched the id. |
| `ambiguous` | Conflicting Element metadata, type mismatch, conflicting Word/metadata binding or multiple schema matches. |

Unresolved controls are never discarded. `link_status` and `path_status` are reported separately
from the overall status, because an id join does not prove that a binding is semantically correct.

## Report

`report.py` produces `ReferenceReport` (reference version `1.0`) with:

- artifact/document/control counts and counts per element kind, classification, resolution,
  link status, path status, part and story;
- `coverage_ratio` = fully resolved controls / all controls (0.0 when a document has no controls);
- `join_coverage_ratio` = controls joined by id / all controls;
- exact duplicate groups and nested-archive inventory;
- a stable `report_digest` over canonical report content;
- a per-control diagnostics trail and `runtime_compatibility: "not_tested"`.

The report is JSON-serialisable and deterministic: lists are sorted and JSON output uses sorted
keys. The denominator is always reported explicitly (unique documents, control instances,
metadata rows), so coverage cannot be silently inflated by duplicate copies.

### First local corpus run

On the maintainer's local, git-ignored copy of the reference corpus, the inspector reproduced the
specification baseline:

| Metric | Count |
| --- | --- |
| Unique DOCX payloads | 17 |
| DOCX occurrences (including duplicate archives) | 63 |
| Content-control instances | 672 |
| Id joins | 650 |
| Explicit unresolved instances | 22 |
| Exact duplicate groups | 37 |

The 22 unresolved instances are `no_element_for_id`; they remain in the report with full location
and marker evidence. These are technical join results, not a judgement that Docentric itself is
broken, and they are not runtime evidence.

## CLI

```bash
# local DOCX
docentric-copilot reference inspect template.docx --json .tools/report.json

# a whole directory, expanding one nested archive level
docentric-copilot reference inspect .tools/reference-corpus/examples/corpus \
  --max-depth 2 --json .tools/report.json

# JSON to stdout
docentric-copilot reference inspect template.docx --json -

# provide a matching bare DDSP schema explicitly
docentric-copilot reference inspect template.docx --ddsp schema.ddsp --json report.json
```

`--max-depth` is offline-only and capped at 3. Exit codes follow the existing CLI contract:
`0` success, `3` invalid/unsupported input, `6` missing input.

## HTTP API

```
POST /api/v1/reference/inspect
```

Either upload a multipart `file` (`.docx`, `.zip`, `.axpp`) with an optional `ddsp` part, or pass
`?path=` for a path confined to a configured corpus root. Query parameter `max_depth` defaults to
`0` for the public endpoint: the root container is enumerated, but nested archives are not
expanded. The existing `max_ddsp_bytes` limit is enforced for uploads and the uncompressed/entry
limits are enforced while reading.

```bash
curl -s -F "file=@template.docx" \
  http://localhost:8000/api/v1/reference/inspect

curl -s -X POST \
  "http://localhost:8000/api/v1/reference/inspect?path=examples/corpus/template.docx&max_depth=0"
```

Corpus roots are configured with `DC_REFERENCE_CORPUS_ROOTS` (comma-separated) and default to the
git-ignored `.tools/reference-corpus`. Symlinks and `..` cannot escape a configured root.

## What is not implemented

- REF-01: a real DDSP parser/normalized schema adapter. Only path extraction from a supplied bare
  DDSP is implemented for REF-02 validation.
- REF-03: ReferenceGraph v1, safe projection to Template IR, import mode.
- REF-04: semantic/structural comparison between reference documents.
- REF-05: reference-based semantic benchmark and gold labels.
- REF-06: web inspector/UI and the `/references/{id}` storage workflow.
- REF-07: licensed runtime testing, AXPP deployment/execution, native Docentric output.
- Any claim or enabling of `target=docentric-ax`. The AX compatibility gate remains fail-closed and
  V5 remains `not_tested`.
